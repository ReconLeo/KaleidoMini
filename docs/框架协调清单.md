## FTK-KM-01：`from .base_plugin import ...` 必然 ImportError

### 现象

插件按"目录化布局"写成相对导入后，框架启动时插件加载失败，插件完全不可用：

```
2026-11-02 19:59:56 - ERROR - system - 导入插件 plugins.kaleido_mini.kaleido_mini 失败:
No module named 'plugins.kaleido_mini.base_plugin'
...
最终注册表内容: ['auth', 'user_manage']     # kaleido_mini 消失
```

后台插件列表里看不到该插件，`/plugin/kaleido_mini` 返回 404，且**安装阶段一切正常**
（`install_plugin.py` 报 `[OK] 安装完成`），因此问题只在启动时才暴露。

### 根因

`base_plugin.py` 位于**上级包** `plugins/base_plugin.py`，而插件被安装为
`plugins/<name>/` 独立子包（框架在安装时自动生成 `plugins/<name>/__init__.py`）。

因此 `from .base_plugin import BasePlugin` 会被解析为
`plugins.kaleido_mini.base_plugin`（本插件子包内），该模块不存在 → `ModuleNotFoundError`。

正确写法是绝对导入（与官方示例 `examples/plugins/multitool_demo/multitool_demo.py:26` 一致）：

```python
from plugins.base_plugin import BasePlugin, permission as permission_required
```

### 最小复现

```bash
# 1) 任意插件，主 .py 顶部写：
#    from .base_plugin import BasePlugin
# 2) 打包 + 安装
python tools/package.py pack src/<name> -o dist/<name>.zip --type backend
python tools/install_plugin.py backend dist/<name>.zip --base <隔离根>
# 3) 启动
cd <隔离根> && python app.py
# 观察：ERROR ... No module named 'plugins.<name>.base_plugin'
```

### 影响面与建议

- **影响**：所有照抄"相对导入"指引编写的新插件，在 v4.21+ 目录化布局下 100% 加载失败；
  且失败发生在启动期、安装期无告警，排查成本高（本次即由端到端测试才发现）。
- **文档需修订**：`flasktoolkit-subproject-dev` 技能 `references/plugin-authoring.md` §2
  与框架开发指南中"源码目录用相对导入 `from .base_plugin import BasePlugin`"的表述，
  在"包内 `<name>.py` + 上级 `base_plugin.py`"这一实际布局下**不成立**。
- **建议框架侧**：安装/加载阶段捕获 `ModuleNotFoundError` 时，若缺失模块名为
  `<plugin>.base_plugin`，直接给出"请改用 `from plugins.base_plugin import ...`"的定向提示；
  或在安装期静态扫描该错误导入并拒绝安装。
- **插件侧 workaround**（已采用，见 `src/kaleido_mini/kaleido_mini.py` 顶部）：

  ```python
  try:
      from plugins.base_plugin import BasePlugin, permission as permission_required
  except ImportError:      # 兼容"插件目录自带 base_plugin.py"的另类布局
      from .base_plugin import BasePlugin, permission as permission_required
  ```

## FTK-KM-02：插件 API 未匹配路径返回 405 而非 404

### 现象

请求一个**不存在**的插件 API 路径时，框架返回：

```
HTTP 405
{"code": 405, "message": "不支持的请求方法 GET，支持的方法: "}
```

注意 `支持的方法: ` 后面是**空的**——这在语义上是自相矛盾的（既然没有支持的方法，
就不可能只是"方法不对"）。

### 根因

`routes/plugin.py` 的 `api_dispatcher` 在"精确匹配 + 正则匹配"都失败后，用如下方式
判断路径是否存在（约 160-179 行）：

```python
path_exists = (
    api_full_path in plugin._wrapped_routes or
    any('<' in path for path in plugin._wrapped_routes)   # ← 恒为真
)
```

只要插件**注册过任何一个带路径参数的路由**（本项目有 4 个），`any('<')` 就恒为 `True`，
于是任意未注册路径都被判定为"路径存在、仅方法不匹配" → 405。

### 最小复现

```bash
# 插件注册了 /qbanks/<subject>/<filename>
curl -i http://127.0.0.1:5000/api/<name>/qbanks/a/b/media/..%2Fescape.png
# 实际: 405 + "支持的方法: "（空）
# 期望: 404
```

### 影响面与建议

- **影响**：客户端无法区分"路径写错"与"方法用错"；监控里 404 指标失真；
  错误提示对用户无信息量。
- **建议**：`path_exists` 应复用同一套 `parse_path_pattern(...).match(api_full_path)` 判定，
  即 `any('<' in p and parse_path_pattern(p)[0].match(api_full_path) for p in rows)`；
  且 405 时若 `allowed_methods` 为空，应降级返回 404。
- **插件侧**：无 workaround（不影响功能正确性，仅错误语义）。端到端用例已按实际行为断言
  "非 200 且不吐文件内容"，并另用反斜杠穿越（能进到处理器）验证插件自身的 400 拦截。

## FTK-KM-03：~~打包/安装 CLI 缺非交互开关~~ —— **已撤回（本人误判）**

### 撤回说明

最初记录为"两个 CLI 缺非交互开关，脚本化必卡"。后续复核 `--help` 与实测后确认
**这条不成立，属本人误判**：

- `tools/package.py pack` **已有 `-y/--yes`**：

  ```
  -y, --yes   输出文件已存在时直接覆写，跳过交互确认
  ```

  实测：`package.py pack <src> -o a.zip --type backend -y` 重复执行时打印
  `警告：输出文件已存在，按 -y 直接覆写` 并成功完成，**完全不交互**。

- `tools/install_plugin.py backend` 在目标已安装时**不交互**，而是明确报错并给出指引：

  ```
  错误：插件 <name> 已存在，更新请加 --update（将按旧 installed_files 清单清理后重装）
  ```

  加 `--update` 即可正常重装。

### 误判原因

当时把 `package.py` 的交互提问（zip 已存在）与紧随其后的安装命令输出混在一起看，
且没有先查 `--help` 就下了结论。教训：**报框架缺陷前必须先查 CLI 的 `--help`
与相关源码，并单独复现**，否则会污染协调清单。

### 正确的使用姿势（无需任何 workaround）

```powershell
python tools\package.py pack src\<name> -o dist\<name>.zip --type backend -y   # 重复打包
python tools\install_plugin.py backend dist\<name>.zip --base <根> --update     # 覆盖安装
```

## FTK-KM-04：页面路由的权限拒绝返回 500 而非 403

### 现象

给 `page=True` 的页面路由加 `@permission_required("admin")` 后，非管理员访问该页面得到：

```
HTTP 500  （"页面加载失败"），而期望是 403
```

同一插件的 **API** 路由用同样的装饰器行为正常（返回 `{"code":403}`）。

### 根因

两处配合导致的类型不匹配：

1. `core/permission.py::wrap_view_func` 对**页面**请求拒绝时返回**元组**：

   ```python
   return render_template('403.html', message="需要管理员权限才可访问"), 403
   ```

2. 但 `routes/plugin.py::plugin_subpage_dispatcher` 只处理两种返回：

   ```python
   result = entry['view_func'](**kwargs)
   if isinstance(result, Response): return result
   ctx = result if isinstance(result, dict) else {}      # ← 元组落到这里
   return render_template(resolved, plugin=plugin, **ctx)
   ```

   元组既不是 `Response` 也不是 `dict`，于是被当成**空上下文**去渲染目标模板；
   模板里用到页面上下文（如 `settings.xxx`）→ Jinja `Undefined` 报错 → 500。

同类问题也会影响"页面视图返回 `self.error_response(...)`"（即 `(jsonify, code)` 元组）的插件，
表现为**本该 404 的页面变成 500**。

### 最小复现

```python
# 插件里给页面路由加管理员权限
{"path": "/settings", "methods": ["GET"], "page": True,
 "template": "settings.html", "view_func": self.page_settings}

@permission_required("admin")
def page_settings(self): ...
```

```bash
# 用普通用户访问
curl -i -b "token=<user token>" http://127.0.0.1:5000/plugin/<name>/settings
# 实际: 500    期望: 403
```

### 影响面与建议

- **影响**：①权限语义错乱——403 与 500 在监控/审计上含义完全不同；
  ②任何在页面视图里返回 `error_response()` 的插件都会踩到，表现为"页面出错就 500"；
  ③新手容易误判为模板 bug 而长时间排查。
- **建议**：分发器在渲染前先识别元组，形如
  `if isinstance(result, tuple) and len(result) == 2: return result`；
  或让 `wrap_view_func` 对页面请求统一返回 `make_response(render_template(...), code)`。
- **插件侧 workaround**（已采用）：
  1. 页面路由**不加** `@permission_required`，改为在视图内自行判权并返回真正的 Response
     （见 `KaleidoMini.page_settings`）；
  2. 页面视图的所有错误分支改用 `self._page_error(msg, code)` 返回
     `make_response(render_template('404.html'/'403.html'/'500.html'), code)`，
     绝不返回 `error_response(...)` 元组（见 `page_bank` / `page_exam`）。

## 附：非缺陷但值得知道的实测结论
1. **静态扫描会把"自属数据目录读写"列为高风险**（`file-read` / `file-write` / 删除文件），
   安装时仅 observe 提示、不阻断；`shutil.rmtree` 属"可约束 high"，
   需在行上标 `# scan:ignore` 才会显示 `[已 # scan:ignore 豁免]`。已在 `km_store._safe_rmtree` 标注。
2. **未安装 auth 插件时** `_check_permission` 直接放行（无登录体系），
   插件内"当前角色"应回落为 `admin`，否则管理入口会被永久隐藏。见 `KaleidoMini._role()`。
3. **`/plugin/<name>` 主入口页的 `request.user` 由 `routes/interceptor.py` 注入**
   （`/plugin/` 命中 `LOGIN_GUARD_PREFIXES`），而插件 **API** 的 `request.user`
   由 `core/permission.py` 的 `_check_permission` 注入 —— 两条路径都能拿到角色，
   但若某插件页面挂在非 `/plugin/` 前缀下则拿不到，需自行回退解析 token。
